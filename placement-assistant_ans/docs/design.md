# Sprint — design notes

Answer each in a short paragraph. Point to the code.

1. Why is the unit of retry the tool call, and not the whole request?
An agent run is a multi-step sequence consisting of model reasoning turns and tool invocations. If the unit of retry were the entire request, any failure or crash mid-run would require replaying all steps from the beginning, risking duplicate execution of external side effects or wasting LLM tokens on already-completed reasoning. By making the individual tool call the unit of retry, `rebuild()` in `app/runner.py` can reconstruct the exact execution state from `run_step` and `tool_call` tables and only replay the specific pending tool call at that sequence number. Combined with `idempotency_key()` in `app/idempotency.py`, already-executed side effects return their stored result without repeating the operation.

2. The idempotency key is stored in placement.db, not agent.db. Why there, and why in the same transaction as the side effect?
Because `placement.db` and `agent.db` are separate SQLite files, SQLite cannot provide atomic dual-database commits without distributed transactions. If the idempotency key were stored in `agent.db` while side effects (like applications, slots, or notifications) were written to `placement.db`, a worker could be killed after writing to `placement.db` but before writing to `agent.db`. On retry, the second worker would see no record in `agent.db` and would execute the side effect a second time. Storing the idempotency key directly in `placement.db` within the same `with self.transaction()` block in `PlacementDb.once()` (`app/placement_db.py`) guarantees atomicity: the side effect and its idempotency key commit together or roll back completely.

3. What happens if the lease is shorter than one model call? What would you change?
If `lease_seconds` expires while the worker is synchronously waiting for `provider.generate()` in `app/runner.py:112`, another worker running `reap_expired()` will assume the worker has crashed, re-queue the run, and claim it. When the original worker finally receives the model's response and attempts `between_steps()` or `complete()`, `heartbeat()` will return `False` and raise `LeaseLost`, aborting the original run while the second worker duplicates the work. To fix this, we should either run a background thread or asynchronous task that continuously heartbeats (`store.heartbeat()`) during active LLM calls, or set `lease_seconds` with a generous timeout margin exceeding the provider's max request deadline.

4. Why do both databases open transactions with BEGIN IMMEDIATE instead of plain BEGIN?
A default SQLite `BEGIN` opens a deferred transaction that only acquires a shared read lock when reading. If two workers both execute `BEGIN`, read candidate rows simultaneously, and then both attempt an `UPDATE` or `INSERT`, each worker tries to upgrade its read lock to a write lock. Because neither can upgrade while the other holds a shared read lock, SQLite aborts one with a "database is locked" error (deadlock). Using `BEGIN IMMEDIATE` (`app/memory.py:36` and `app/placement_db.py:65`) acquires the reserved write lock immediately at the start of the transaction. Any second worker attempting `BEGIN IMMEDIATE` queues up and waits up to `PRAGMA busy_timeout` (5000 ms) instead of deadlocking.

5. Name one thing in this system that is still not exactly-once, and what it would take to fix it.
Real external outbound message delivery (such as sending SMS/email in `notify_student` or external API calls). While `record_notification` dedupes rows in `placement.db`, interacting with an external SMS gateway or email service cannot share a local SQLite transaction. If a worker calls an external gateway API and crashes before committing the database transaction, the SMS has already been sent to the student's phone, but the local database rolls back; the replayed run would then send the SMS a second time. Fixing this requires an Outbox Pattern: inserting the pending message atomically into an outbox table, having a dedicated sender worker dispatch messages with external idempotency keys supported by the upstream gateway provider, and acknowledging receipt only after delivery confirmation.
